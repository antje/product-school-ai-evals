## Fallback methods (non-Level 3 items)

### L2 · Context Specificity (UX Trust · P1)
- **Method:** Two parts, both cheap. Every session logs whether the user re-asks or reformulates the same question within five minutes, a sign the answer missed what was asked, tracked as a rate per account. A weekly human audit of 30 sampled answers checks each answer against what the question asked for, oversampling sessions with a re-ask.
- **Why this fallback is defensible:** Context misses fail in plain sight: the VP asked for the negative reviews, got all of them, and asks again. The user is the detector, so we instrument the user instead of paying a judge to find what the user already sees. That frees Level 3 for Source Attribution, which fails where nobody is looking: a citation to the wrong but related table looks verified, goes into a board deck, and surfaces months later in the client's own audit. Data Fabrication and Source Attribution share one Level 3 judge that checks each claim against the source it cites before the answer is sent, and holds flagged answers for a human, as the Module 3 eval spec requires. The cost of this trade is a slower read on nuance misses that users put up with without re-asking; those surface only in the weekly audit.

### L2 · Data Bias (Fairness · P2)
- **Method:** Code counts the share of US and APAC sources in every multi-region answer against their share in the retrieved set, and flags answers that lean further than their sources. A bi-weekly human audit of 40 multi-region answers checks framing, which code cannot see: an answer can cite APAC sources and still lead with US conclusions.
- **Why this fallback is defensible:** Regional skew builds as a pattern across many answers, so a per-answer judge would spend Level 3 money rediscovering the same lean. The source count runs on all traffic at code cost, and the human hours go to framing, the part only a reader can judge. The exposure is real: for an APAC-heavy client, a skewed answer can steer a market-entry decision, which is why the automated count runs on every answer rather than on a sample.

### L1 · Cost Overruns (Latency · P3)
- **Method:** A hard per-request cap on tokens and agent steps in the runtime, which stops a runaway loop outright. On every release, the cost dimension of the CI gate warns when a change drops its 0 to 100 score by more than 5 points against main, as set in the Module 4 CI policy. A billing alert on tokens per request backs both up.
- **Why this fallback is defensible:** Token use is metered exactly, so there is nothing for a judge to interpret. The realistic overrun is a runaway loop on a real query, which a release gate on fixed fixtures never sees; the per-request cap stops it at the source. That is also why the third Level 3 slot stays empty: $25K of continuous judge monitoring would measure what the invoice already measures, and the remaining $50K of Level 3 headroom cannot buy Data Bias ($55K) at Level 3.
